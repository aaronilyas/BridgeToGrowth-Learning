# BridgeToGrowth mobile frontend

Native React Native/TypeScript app using stable Expo SDK 57, Expo Router,
TanStack Query, built-in fetch, SecureStore, NetInfo and AppState. It implements
login, signup/phone verification and resend, password recovery/reset, lesson
submission/progress/cancellation, account details, logout/all and verified phone
changes against the existing FastAPI API. No backend or messaging behavior changes.

## Setup and commands

Use Node **22.13 or newer** (verified with 22.22.1) and npm. From this directory:

```sh
npm ci
cp .env.example .env
# Edit EXPO_PUBLIC_API_BASE_URL to the deployed public HTTPS FastAPI origin.
npm start
# With native build tools installed:
npm run android
npm run ios

npm run typecheck
npm run lint
npm test
npm run check:expo
npx expo-doctor
npm run export:native
npx expo prebuild --no-install
```

`EXPO_PUBLIC_API_BASE_URL` is public configuration embedded in the app, never a
secret. Supply an origin only, without a path, credentials, query or fragment.
Missing/invalid configuration displays a setup screen. Use HTTPS in builds;
HTTP is allowed only in development for a deliberately configured local API.
Use an address reachable from the device, rather than its own localhost. API
credentials, Gemini/Photon secrets and private callbacks belong to the backend.
No `.env` files or generated native projects are committed. Restart Expo after
changing environment configuration. Native projects are generated by prebuild.

The mobile target is iOS/Android; there is no browser token-storage fallback.
SDK 57 targets React Native 0.86.3 / React 19.2.3. Package versions were selected
by `expo install` and verified by Expo Doctor. ESLint 9 is pinned because the
Expo React lint plugin currently fails with ESLint 10. Jest requires the matching
`@react-native/jest-preset` and React Native Testing Library 14's `test-renderer`
peer. Sources: [Expo compatibility](https://docs.expo.dev/versions/v57.0.0/),
[Router installation](https://docs.expo.dev/router/installation/),
[Jest](https://docs.expo.dev/develop/unit-testing/),
[Router tests](https://docs.expo.dev/router/reference/testing/),
[SecureStore](https://docs.expo.dev/versions/v57.0.0/sdk/securestore/),
[TanStack Query native lifecycle](https://tanstack.com/query/latest/docs/framework/react/react-native).

## API contracts and documentation conflicts

The source of truth is `backend/main.py`, `auth.py`, `service.py`, their tests,
[AUTHENTICATION.md](../backend/AUTHENTICATION.md) and the
[lesson API](../backend/README.md). Historical prompts and integration notes
predate this frontend. The product overview's aspiration to report receipt does
not make acceptance a receipt: only correlated read evidence permits that label.
There is no lesson-list endpoint or lookup by idempotency key. Legacy enrollment
remains an operator-supported backend flow; it is not invented as alternate login.

Payloads use exactly the supported fields. Phone numbers use E.164; passwords
are preserved exactly, validated as 12–128 Unicode characters and never persisted.
Codes remain six-digit strings. Topics trim to 1–10,000 Unicode characters.
Voiceover starts off. Requests reject duplicate taps, do not retry mutations
in the background, and honor challenge expiry, five attempts, resend cooldown
and HTTP `Retry-After`. Neutral challenge messages never claim a message was sent.
Resending neither extends challenge expiry nor resets attempts. Network-uncertain
verification attempts are counted conservatively; a definite throttle is not.
A reset requires login. Phone verification revokes sessions and requires login
with the new number; an already-started message can reach the old number.

## Session storage and race handling

Access tokens and account details live in memory. The single SecureStore session
record contains only account ID, refresh token and absolute expiry. iOS writes
use `WHEN_UNLOCKED_THIS_DEVICE_ONLY`; no biometric prompts or AsyncStorage are
used. A conservative request-start time bounds token expiry. Refresh rotation
never extends the original absolute refresh deadline.

One client-wide refresh promise holds new authenticated requests until rotation
finishes. Before contacting `/auth/refresh`, a durable blocked marker replaces
the stored credential. A process exit or lost response therefore cannot restore
a possibly consumed token. The rotated refresh credential is securely saved
before either new token is usable. Uncertain network responses, malformed tokens
and unsafe storage failures sign out; consumed credentials are never retried.
A definite 429 is safe to retain because this backend throttles **before** token
consumption; the unused credential is restored only if that write succeeds.
An in-flight read using the previous bearer may retry after known rotation;
an in-flight mutation gets a manual-retry error and is never replayed.

Session restoration gates all protected routes and checks `/account` before
exposing account data. Offline restoration offers manual retry or local logout.
Session teardown immediately advances an epoch, aborts requests, cancels/clears
account queries and removes in-memory pending work. Late responses cannot restore
old account data. Ordered storage writes prevent teardown and new installation
from overwriting each other. Logout attempts the appropriate server revocation
before local cleanup; its message distinguishes confirmed revocation from a
local-only logout. A blocked marker remains if deletion fails. If both marker
writing and deletion fail, further account installation is blocked and the UI
requires clearing app storage. No client can guarantee durable deletion while
the OS refuses every storage operation; device fault testing remains necessary.

## Submission and recovery limits

Each deliberate request gets an `expo-crypto` UUID. Before submission, SecureStore
retains an account-scoped record with key and time; after acknowledgement it also
retains the job ID. At most six records are retained. No topic text is stored
there, and unresolved records are never silently evicted. Corrupt metadata fails
closed. The normalized payload is immutable in memory. Explicit retry reuses
both key and payload; editing/preparing a new request creates a new key.
A lost or malformed response does not automatically issue another request.

Known IDs can be checked after an app restart while restoring the same session.
A key without an ID cannot be recovered by this backend, and the original
payload does not survive restart. No empty lookup is treated as permission to
resubmit. The UI explains that a new request may produce another message and
requires acknowledgement when there is an unresolved key. Removing a local
record requires a separate confirmation and does not cancel server work or
retract a message. Signing out clears these device records; they are local
tracking, not server-backed lesson history. If ID persistence fails after success,
the in-memory ID remains available until the process ends.

## Progress, cancellation and message semantics

All backend stages/outcomes have readable messages, including legacy requested,
processing, needs_breakdown, failed, cancelled, interrupted, delivery_unknown
and accepted. Unknown statuses explicitly leave the outcome unconfirmed.
Active jobs and pending cleanup poll every four seconds, with error delays up
to 30 seconds. Offline/background polling pauses; returning reconciles active
work. After eight consecutive errors or a 404, automatic checks stop and manual
refresh is available. Throttles pause requests until their retry deadline.
Terminal jobs with complete cleanup stop frequent polling. Accepted jobs receive
at most eight further automatic receipt checks per mounted view, then require
manual refresh. Returning to a retained job is a deliberate new observation.
There is no endless account/terminal-job heartbeat to keep idle containers alive.

Cancellation acknowledgement expresses intent; status is refetched to learn the
actual outcome and cleanup state. Conflicts and lost cancellation responses also
trigger observation. Messaging cutoff disables cancellation. No already-sent
message can be retracted. `delivery_unknown` may already have sent and is never
automatically retried. Photon acceptance confirms provider acceptance only;
reading is shown only for an accepted job with provider ID, acceptance flag,
`receipt_status: read` and a valid server-provided `read_at`. Missing read evidence
stays unconfirmed. The current provider is iMessage, with no universal Android
recipient or SMS fallback promise. No generation time is promised.

## Verification and remaining integration

Deterministic Jest tests use mocked fetch/native storage/lifecycle and Expo
Router + React Native Testing Library. They cover refresh serialization, lost
rotation responses, marker/save/deletion failures, absolute expiry, stale-account
isolation, challenge limits, exact passwords/codes, idempotency/lost responses,
polling pause/resume/termination, cancellation races, receipt distinctions,
protected deep links and core screen interactions. Tests send no messages and
contact no provider. Native exports/prebuild validate bundles/configuration;
they are not proof of successful execution on a physical phone.

This environment lacks Android SDK/emulator and Xcode, so native compilation,
OS Keychain/Keystore behavior, app background termination, screen readers,
large-text/keyboard/device layouts and real frontend-to-backend integration need
verification on intended test devices. Real verification/video messages, Photon
recipient eligibility/read-receipt behavior and production TLS require separately
authorized testing. Gemini quality, generated code/container execution, lifecycle
and temporary video handling remain entirely backend-owned. No videos are
stored, played or downloaded by this app.

`npm audit` currently reports transitive advisories in the compatible Expo/Jest
stack (including Metro/braces, forge, URI decoding and test tooling). Compatible
`npm audit fix` makes no further changes. Major-version force fixes would change
the selected stable SDK or test preset and were not applied; review upstream
patches before production distribution. The checked-in lockfile reproduces the
verified versions.

Verified locally: fresh `npm ci`, strict typecheck, lint, Jest (82 tests across six suites), Expo
package compatibility, Expo Doctor (21/21), Android/iOS Hermes bundle exports,
and native prebuild with `--no-install`. Backend files are unchanged, so backend
checks were not rerun for this frontend-only change. Audit reports 60 transitive
advisories (15 moderate, 45 high) in this lockfile; the audit is not a passing check.
